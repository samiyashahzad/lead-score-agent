LeadScout Reliability Audit

An engineering case study evaluating the reliability and factual grounding of the LeadScout LLM pipeline under specific failure conditions and ambiguous inputs. The system processes raw inquiries through a multi-stage pipeline: extracting categorical signals via LLM, applying deterministic business logic to score the lead, and generating an LLM-driven explanation and recommended action.

Where the System Broke

The system was evaluated against the live LeadScout API using the production threading.Semaphore(5) constraint. Concurrency levels were run independently to isolate provider quota effects.

Concurrency = 1 20/20 Success • ~310s • p50 ~15.6s • p95 ~22.5s
Concurrency = 5 7/20 Success • ~72s • p50 ~15.2s • p95 ~20.8s
Concurrency = 10 8/20 Success • ~85.5s • p50 ~34.2s • p95 ~48.9s

Finding: The provider's 8,000 tokens-per-minute (TPM) quota was the hard bottleneck. The C5 vs C10 success percentages should not be interpreted as an improvement because provider throttling heavily affected the runs and repeated controlled trials were not performed.

Generative Boundary

The generate_explanation() function intentionally does not receive the raw lead inquiry, acting as a strict architectural boundary. We tested whether the LLM introduces unsupported factual specificity beyond the structured evidence available to it.

  • 11/12 clearly grounded on manual review.
  • 1/12 borderline unsupported goal framing ("to secure a distribution partnership").
  • 0 clear factual hallucinations observed (no invented people, times, products, or locations).

Note on Lexical Evaluators: A simple rule-based priority-policy checker incorrectly flagged the generated phrase "no immediate action required" as a Warm/Hot violation because it contained the word "immediate". This false positive highlights the brittleness of pure string-matching for evaluating policy alignment.

When the Ground Truth is the Problem

We consolidated an existing urgency experiment utilizing the typesafe-ai/jev evaluator model against 9 cases in the baseline dataset. Jev matched the expected urgency label in 7/9 cases. The two disagreements exposed ambiguity in the underlying specification rather than strict model failure:

Case F: multi_branch_distributor_hot
"...would like to explore stocking your product line..."
Expected: low Jev: unknown

Specification Ambiguity: The original label interpreted pacing/hedging language ("explore") as low urgency. Jev strictly followed the prompt ("no time-related language → unknown").

Case I: large_enterprise_end_customer
"...want to set up a regular supply contract... send pricing for national-level procurement."
Expected: medium Jev: unknown

Label Ambiguity: The inquiry indicated high business seriousness but contained no explicit timing evidence. Dataset labeled it medium, Jev marked unknown.

Conclusion: These disagreements exposed ambiguity in the urgency specification and existing labels. This experiment is not sufficient to rank models; it simply highlights that the ground truth requires tightening before acting as a reliable benchmark.

Not Every Finding Deserves a Fix

Category Status Rationale
Unhandled 429s Fixed Implemented bounded retries and structured 503s to prevent client 500s.
Concurrency Limit Left Alone Semaphore(5) bounds simultaneous LLM calls but does not enforce the provider's token-per-minute quota.
Next-action grounding Left Alone No clear factual hallucinations were observed in the 12-generation targeted review; evidence did not justify a production change.
Dataset Ambiguity Documented Urgency instructions and labels require an alignment pass before further benchmarking.

Methodology & Limitations

This audit is a constrained point-in-time reliability investigation. Please note the following critical limitations:

  • Not General Benchmarking: Concurrency results are highly specific to the tested provider, model, tier (8,000 TPM limit), and exact payload size.
  • No Claim of Model Superiority: The Jev cross-model audit only highlights dataset ambiguity and cannot be used to prove one model is "better" than another.
  • No Production Deployment or User Validation: Findings and fixes were evaluated locally or via mocked boundaries (e.g., patched sleep durations). None of this implies production deployment or end-user validation.
  • Sample Size constraints: Next-action grounding was manually reviewed across only 12 generated next actions across four controlled structured-input states.
